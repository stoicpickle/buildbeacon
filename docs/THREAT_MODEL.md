# Threat model

BuildBeacon 0.1 is an experimental visual transport for public, signed build claims. It is not a complete supply-chain trust system and is not a media-authenticity system.

## Assets

- exact canonical receipt bytes;
- integrity of the receipt signature;
- the signer’s private key outside the browser demo;
- the verifier’s explicitly pinned public-key fingerprints;
- bounded receiver CPU and memory;
- user privacy while decoding local clips or camera frames.

Receipt contents, public keys, signatures, identifiers, and QR frames are not confidential data; anyone who can see the beacon can reconstruct its payload. User-selected clips and camera frames may be highly sensitive. BuildBeacon processes them locally in the tab, never intentionally transmits them, and treats their privacy as an asset.

## Security goals

Given enough valid frames from one beacon, the implementation aims to:

- reconstruct the exact signed envelope despite join-late starts, reordering, duplicates, and erased frames;
- discard malformed or corrupted frames before they enter the equation matrix;
- prevent frames from different receipts or incompatible stream parameters from contaminating one decode;
- detect changes to canonical receipt bytes through Ed25519 verification;
- distinguish a self-presented verification key from a separately pinned trust anchor;
- keep browser media processing local and stop camera tracks on exit;
- reject attacker-controlled sizes, nesting, unknown fields, and excessive frame counts.

## Explicit non-goals

BuildBeacon does not:

- prove that visible footage was generated by the artifact named in the receipt;
- bind the beacon to surrounding pixels;
- detect edits outside the beacon;
- prevent copying or replaying a valid beacon over unrelated footage;
- prove a repository, commit, artifact, test result, builder, workflow, or timestamp actually existed;
- provide trusted time, freshness, anti-replay, key discovery, identity, rotation, revocation, or compromise recovery;
- survive removal, severe blur, occlusion, adversarial QR replacement, or cropping the marker away;
- encrypt receipt contents;
- verify C2PA, SLSA, Sigstore, or GitHub artifact-attestation formats;
- establish novelty, patent clearance, or freedom to operate.

## Attacker cases

### Modified receipt

Changing a receipt or signature invalidates canonical decoding, the receipt ID, or the Ed25519 signature. A verifier must never show build claims as signed when signature verification fails.

### Replacement or replay overlay

An attacker can paste a complete, valid beacon onto another recording. BBP/1 cannot distinguish this from the original transmission. Consumers must describe the result as “the pixels contain this signed receipt,” not “this footage came from this build.” Content binding requires a separate media-provenance mechanism.

### Self-presented key substitution

An attacker can create a new key, sign false claims, and carry that public key in the envelope. The math is valid but the identity is unknown. Trust requires an out-of-band pinned fingerprint or a later integration with an identity-bearing attestation system.

### Corrupt, mixed, or oversized frames

CRC32C, receipt IDs, stream-parameter checks, exact packet lengths, maximum 32 source blocks, maximum 128-byte symbols, and a 512-unique-frame ceiling constrain this path. CRC32C is accidental-corruption detection, not a cryptographic MAC; final receipt-ID and signature checks provide cryptographic integrity.

### Browser media input

Uploaded media is limited to 250 MiB, 120 seconds, 4,096 pixels on either side, 16 megapixels, and 960 sampled frames. Decode canvases are capped at 960 pixels on either side. Scans have bounded event waits and an explicit cancellation token. Media is read through a local object URL and never transmitted by BuildBeacon. Camera access begins only after a button press; stale or failed permission/playback operations stop any acquired tracks. Tracks are also stopped when requested, after successful recovery, or when the component unmounts. This repository includes no analytics, accounts, remote verifier, or third-party scripts.

### Private-key exposure

The browser creates only ephemeral demo keys. The CLI accepts a private key from a file or stdin, refuses overly broad POSIX file modes, and does not accept key bytes through argv, query strings, browser storage, or environment variables. JavaScript cannot promise secure erasure; use a real signing service or hardware-backed system for valuable keys.

The fixed key in `scripts/generate-demo-fixture.ts` is public RFC 8032 test material. Any receipt signed by it is a fixture, not trustworthy evidence.

## Dependency boundary

The implementation delegates Ed25519 to `@noble/ed25519`, deterministic CBOR to `cbor2`, QR rendering to `qrcode`, and pixel decoding to `jsQR`. Those libraries and BuildBeacon itself may contain defects. The current `@noble/ed25519` 3.x rewrite does not claim an independent audit of that version. BuildBeacon 0.1 has not been independently audited.

## Operational guidance

- Pin the full `sha256:` public-key fingerprint through a channel independent of the footage.
- Keep private keys outside repositories and CI logs; prefer dedicated signing infrastructure for durable identities.
- Treat all receipt fields as signer assertions until verified against their native system.
- Retain the original attestation or build evidence; BuildBeacon should carry it or its digest, not replace it.
- Publish test conditions with any resilience claim. “Any fragment” always means a sufficiently long fragment containing enough readable, independent frames.

Report vulnerabilities privately through the process in [`SECURITY.md`](../SECURITY.md).
